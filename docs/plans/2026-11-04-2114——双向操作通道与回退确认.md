# 双向操作通道与回退确认

定位：把 IDEA → pi 的控制操作从 Terminal 文本输入迁移到双向 bridge；先确认 pi 执行结果，再提交 IDEA 的业务状态。连接、请求状态、去重和恢复由公共层承担，rewind 是第一个接入业务，不为每条指令重做一套协议。

基线：dev `672f934`；核实日期：2026-11-04。本文件是设计方案，不代表运行代码已经实现。用户已确认方向及未知结果策略；其余标为“建议”的技术选择作为实施默认值，重大偏离须重新确认。本轮仅新增方案，不改插件版本、不构建、不 push。

### 1.1 已核实的现状，不把推测当根因

- `PiConversationService.rewindConversation` 先裁 `messages`、覆盖 draft 并 persist，之后才 `sendText`；没有执行回执，Boolean 不能表达远端成功。
- `PiTerminalService.sendText` 使用 bracketed paste + 延迟 80ms Enter；这是输入投递，不是操作协议。
- `PiBridgeServer.endpoint()` 只证明本地 server 存在；Terminal 存活也不证明当前 extension 可用。
- 当前 extension 每事件独立建立 TCP 连接，写完即结束；server 没有反向操作路由、握手、heartbeat 或请求表。
- `/bridge-rewind` 用索引和文本寻找用户消息，索引不符时从后往前按文本找；重复文本与面板删除会产生目标歧义。
- 当前导航调用是 `ctx.navigateTree(entry.parentId)`，忽略返回的 cancelled；parent 为 null 则提前警告。成功不回执，异常只有 UI notify；部分警告误用 `warn`，公开级别是 `warning`。
- 当前测试 mock 的 navigateTree 只记录调用、不真实更新分支；没有取消、断联、回执丢失或持久恢复覆盖。
- **尚未复现用户第一次 rewind 不动的具体原因。** idle 条件排除了一个猜测，不能证明是 Enter 被吃掉；无通知也不能证明 handler 未执行。

### 1.2 pi 能力核实与适用边界

本机被核对的 `@earendil-works/pi-coding-agent` 为 **1.5.0**，不是用户实际终端版本的证明：

1. `navigateTree` 属于 ExtensionCommandContext，不在普通事件上下文中开放。
2. `pi.sendUserMessage(内部命令, { expandPromptTemplates: true })` 可进入扩展命令分发；已匹配命令时先执行 handler 并返回，不启动模型请求。
3. `sendUserMessage` 的扩展 API 返回 void，不能把它的返回当执行回执；回执必须由内部 handler 显式产生。
4. InteractiveMode 的 navigateTree wrapper 会重绘聊天区并显示导航状态，取消时返回 cancelled；直接修改 sessionManager 不能替代这层行为。
5. user/custom_message 导航目标具有“回到其 parent”的语义。因此“导航到选中消息的 parent”并非对任意 parent 类型都等于精确停在 parent；未回复连续用户消息尤其需要验证。
6. 文档只支持静态可行性判断，实际版本和 TUI 集成实验是实施准入门槛；不假定所有 1.4 或其他发行版具备相同能力。

## 2. 对外契约

### 2.1 四层职责，禁止跨层耦合

| 层 | 负责 | 不负责 |
|---|---|---|
| Transport | 有界帧解码、认证握手、连接路由、心跳、重连、写队列 | rewind、裁剪面板、重放操作 |
| RequestCoordinator | requestId、状态机、超时、去重、日志、只读恢复查询、按会话互斥 | 文本定位、树导航、草稿覆盖策略 |
| PiCommandAdapter + Registry | 获取新鲜命令上下文、查找注册操作、校验参数/能力、执行并核验后置条件 | 终端键盘模拟、IDEA UI 更新 |
| ConversationOperations | 定位目标、准备本地快照、验证结果、EDT 幂等提交、冲突提示 | socket、计时器、重连和协议 JSON |

面板只调用 `requestRewind(conversationId, messageIdentity)` 并订阅 OperationHandle 状态。现有 Boolean 应替换为明确的“本地拒绝 / 已创建操作句柄”，不再称 true 为远端成功。

概念接口（设计签名，非可直接编译代码）：

```kotlin
interface BridgeOperations {
    fun <P, R> submit(peer: BoundPeer, operation: OperationSpec<P, R>, payload: P): OperationHandle<R>
    fun query(handle: OperationHandle<*>): CompletionStage<OperationSnapshot>
}
// Handle 提供 requestId、状态订阅、结果；不暴露通用 retryExecute()。
```

```typescript
registerOperation({
  name: 'conversation.rewind', version: 1,
  effect: 'sessionMutation', concurrency: 'exclusiveSession',
  validatePayload, checkPreconditions, execute, verifyPostcondition,
});
// 公共 runtime 负责去重、持久状态、回执和异常归一化；handler 不写 socket。
```

只读操作可声明并行；修改类操作不提供自动重试选项。未来添加新指令原则上只新增 descriptor、executor、业务提交器和契约测试，不修改 Transport。会换 session 的 fork/switch 后续使用明确的 replacement lifecycle 扩展点，不能伪装成普通 same-session 操作。

### 2.2 双向控制连接与能力协商

- 在现有 server 上新增 v2 控制连接；第一帧 hello，携带 token、tabKey、extension/runtime 版本、bootId、sessionId、sessionEpoch、capabilities。server 返回 welcome/connectionId。
- bootId 每次 extension runtime 创建随机生成；sessionEpoch 在会话切换时递增；connectionId 每次重连更新。三者不能混用。
- connection 状态与 agent working 分开：DISCONNECTED → CONNECTING → HANDSHAKING → READY；不兼容为 INCOMPATIBLE。READY 也不是未来执行一定成功的承诺。
- 仅接受已知 conversation/tabKey 和绑定相符的 peer；bootstrap 尚未绑定时先做首次绑定确认，再开放操作。相同 tab 两个不同 bootId 同时存活时不得按“最后连接者获胜”，先标冲突并核对 Terminal 生命周期。
- 建议参数：握手 5s、heartbeat 5s、15s 无回应视为失联；重连 0.5–10s 指数退避并加抖动。重连可以自动，execute 不可以自动重发。
- 旧 v1 状态事件与 v2 operation_result 不共用 `(tabKey,type)` last-seq 去重。每个请求有独立结果状态；晚到的 A 结果不能被 B 的更大 seq 丢掉。
- 帧使用 newline JSON，UTF-8 流式解码，有界 64KiB（字节）缓冲，必须在整行分配前限制；超长、恶意类型、未知 operation、无限连接和写队列都有边界。
- token 仅限本机用户环境，不是强安全隔离；日志不输出 token、完整 payload 或用户文本。不能开放任意命令、shell 或 eval。

### 2.3 请求与结果信封

控制帧共享 `v=2, type, connectionId, tabKey, bootId, sessionId, sessionEpoch`，认证连接内不必每帧复制 token。

| type | 内容/语义 |
|---|---|
| operation.execute | requestId、operation/version、payload、payloadHash、expectedRevision、startDeadline |
| operation.accepted | 已登记请求；**不意味着已经执行，更不意味着成功** |
| operation.result | requestId、payloadHash、status、errorCode/message、before/after revision、result |
| operation.query | 同一个 requestId 与原始身份；只读查询 |
| operation.status | ACCEPTED/RUNNING/SUCCEEDED/REJECTED/CANCELLED/UNKNOWN/NOT_FOUND；NOT_FOUND 不是“肯定没执行” |
| operation.result_ack | IDEA 已耐久记录结果/本地提交，供结果缓存回收；ack 丢失不会再次执行 |
| ping/pong、snapshot | 连接存活及带版本的只读会话摘要 |

requestId 为随机 UUID，payloadHash 由规范序列化后的 operation/version/目标身份/payload/前置条件产生。重复 ID 同摘要返回已有状态；同 ID 不同摘要报 REQUEST_ID_CONFLICT。网络层只允许一个显式 execute 入队，库不得自动 retry 写操作；TCP 自身重传不算应用层重放。

统一错误：UNSUPPORTED、NOT_CONNECTED、BUSY、STALE_SESSION、STALE_REVISION、TARGET_NOT_FOUND、AMBIGUOUS_TARGET、CANCELLED、POSTCONDITION_MISMATCH、INTERNAL_ERROR。只有确定没有副作用的拒绝才是 REJECTED；执行途中抛错且无法确认是否改变树，归 UNKNOWN，而不是随便报失败。

### 2.4 状态与本地提交契约

```text
PREPARED → SENT → ACCEPTED → RUNNING → SUCCEEDED → LOCAL_APPLIED
     └→ NOT_SENT          └→ REJECTED / CANCELLED（确认无副作用）
SENT/ACCEPTED/RUNNING → UNKNOWN → 查询终态 / 保持 UNKNOWN
SUCCEEDED → LOCAL_CONFLICT（本地或远端版本已变，不盲目裁剪）
```

- 未写入连接且可证明未发出的请求为 NOT_SENT；开始写入后即便 write 报错也可能已送达，按 UNKNOWN。
- 超时只结束等待，不取消远端执行。建议 3s 未 accepted 显示缓慢，15s 未终态转 UNKNOWN；handler 真正开始前核对 startDeadline，过期且尚未执行可明确拒绝。不能把客户端超时说成远端已经停止。
- 用户继续编辑 draft：成功提交时仅在 draftRevision 未变时填入回退文本，否则保留当前草稿，并提供“回退文本待恢复”入口。不丢用户新输入。
- 同一个终态只提交一次。成功后若会话换绑、历史 revision 改变，或查询快照显示远端已继续前进，进入 LOCAL_CONFLICT，展示结果和差异，禁止按旧索引删除。
- 只切换查看另一个 tab 不取消请求；绑定发生变化才使旧结果无法自动应用。旧结果仍记录在原请求上，不得改新会话。

### 2.5 持久化与扩展边界

建议 IDEA 增加独立 OperationStore，原 conversation store 增加兼容的 appliedOperationId/revision 或同等幂等提交标记。请求发出前耐久保存请求身份和本地 preimage 标识；本地提交与 applied 标记一并持久化，崩溃后先对账再开放冲突操作。

pi 侧使用插件拥有的独立操作日志目录，路径由 IDEA 启动配置传入（与 extension 安装目录分离）；不要把结果日志 append 到 session tree，这会改变 leaf/revision。只保存请求摘要、目标 entryId、状态及必要结果，不保存整段用户文本。文件权限、原子写入、进程隔离和 retention 封装在 OperationJournal。

执行前先耐久记录 ACCEPTED/RUNNING；执行成功并核验后写终态，再发回执。**树导航与日志写入不是原子事务**：执行成功后、终态落盘前崩溃，恢复为 UNKNOWN，绝不再次执行。新 bootId 可以查询原日志，但不能用旧 bootId 的 execute 继续运行。

已 ack 的终态建议保留 7 天并有容量限制；未决记录不静默淘汰，容量不足时拒绝新修改操作并提示清理。最小 tombstone 保留请求身份与摘要；缺失记录统一返回 NOT_FOUND/UNKNOWN，不把缺失当重放许可。日志损坏也不能解除未决保护。具体路径、持久格式及容量列入实施任务。

## 3. 运行流程

### 3.1 启动与内部命令适配

1. extension 注册唯一保留内部命令（例如 `pitb-dispatch-<runtimeNonce>`），建立 operation registry、input 安全拦截器及连接生命周期。
2. socket 收到请求仅做解码、身份/摘要校验和登记；以 `pi.sendUserMessage('/内部命令 ' + requestId, { expandPromptTemplates: true })` 唤起调度，不携带正文，不操作 TUI 编辑器。
3. 内部 handler 从受信任 pending 表取请求，获取本次新鲜 CommandContext，检查 deadline、session/revision、idle 与互斥，分派业务 executor。未登记的手工内部命令直接拒绝。
4. 接入前先核实发行版/能力；再做无副作用 dispatch probe，确认内部 handler 实际收到命令。若未匹配命令，input hook 拦截保留前缀，禁止它变成模型 prompt；probe 不通过就不宣告 mutation capability。不能只检查 options 字段存在。
5. session_shutdown/reload 销毁旧连接和定时器、撤销 ready；新的 extension factory 重新握手，不复用旧 pi/ctx。

### 3.2 rewind 正常路径

1. 面板点某条消息时，传稳定本地 identity，不依赖可能变化的卡片闭包 index。业务层保存 messagesRevision、draftRevision 与原 pi 绑定。
2. 通过只读 snapshot/resolve 获取当前 branch revision 与目标 userEntryId；若已有准确映射直接用，旧历史按文本摘要与有序上下文进行保守匹配，重复内容无法唯一确定时拒绝，不再 newest-first 猜测。只读解析即使重试也不得修改树。
3. snapshot 使用分支摘要（含 leafId、相关 entry IDs/内容摘要）作为 expectedRevision；不能只依赖 leafId，原地 context edit 等也可能改变语义。大历史分页/分块并固定 revision，超过资源上限明确拒绝，不静默截断。
4. 请求准备持久化后，先锁该会话的冲突操作，再且仅再发送一次 execute。消息和草稿保持不变。
5. pi executor 再次核对当前会话和 revision，确认目标在活跃分支且符合 rewind 契约，检查忙碌状态；不自动 abort，不等待后续 idle，不抢占用户操作。
6. 执行导航，检查 cancelled，并核验 afterLeaf/活跃分支和 session 身份；成功证据耐久写入后发 result。回执代表 wrapper 返回和状态核验，不代表显示器已经完成一帧绘制。
7. IDEA 在 EDT 核对 requestId、payloadHash、peer、session、local revision 和结果；应用一次裁剪、草稿恢复或保留新草稿，持久化并刷新历史。网络和日志 I/O 不在 EDT 阻塞。

导航策略建议首期保持现有“回退到所选消息之前、文本只回 IDEA 草稿”的业务语义。`parentId` 非 user/custom_message 时使用现有导航目标；root、parent 为 user/custom_message、当前 leaf 恰等于目标等特殊情形必须在执行前单独判定，未验证支持则明确 UNSUPPORTED_TARGET 并保留面板。不能先执行多退一条，再仅靠后置检查告诉用户失败。后续可验证导航到 userEntryId 并安全保留 TUI 编辑器内容的方案，但不在本次偷偷改变首条/未回复消息行为。

### 3.3 断联、超时与重连

- 发送前已断联：明确未发送，消息不动。
- 请求可能已到达、未收到终态：UNKNOWN，保留 IDEA 状态；提示“执行结果未确认，正在查询；请勿重复回退”。
- 网络恢复：握手并核对运行时身份，然后只发送 operation.query(originalRequestId)。收到 RUNNING 则继续有限频率查询；收到终态走正常提交/冲突流程。
- 收到 SUCCEEDED 但当前 branch 已继续变化：历史成功事实仍成立，但不能把旧 after-state 当当前状态；显示 LOCAL_CONFLICT，重新读取快照，对账后由用户确认同步，不再次 rewind。
- 收到 NOT_FOUND、日志丢失、执行窗口崩溃：保持 UNKNOWN。单凭“目标不在当前分支”不能证明这个 request 执行过。
- 用户手动“查询结果”仅查询。没有自动“再试一次”按钮；若最终无法判定，提供“查看诊断/对账”流程，确认权威当前分支和本地历史后结束未决，用户才可发起新的独立操作。结束跟踪不等于取消已发请求；旧执行器可能仍在运行时不能解除互斥。
- 进程重启后原请求不得重放。旧日志终态可恢复；RUNNING 记录视为崩溃未决。只有证明旧进程已退出/请求已终结并完成对账，才允许解除保护。

### 3.4 并发与生命周期

公共层提供每 session 独占修改门闩，业务层同时保护本地消息删除/发送等入口。外部用户仍可能直接在 TUI 发消息或 `/new`，本框架不能锁住整个 pi；通过前置 revision、执行后核验、session 事件和提交前新鲜快照检测冲突。存在无法原子锁定的跨进程窗口，按 UNKNOWN/LOCAL_CONFLICT 处理，不宣称强分布式事务。

关闭 project 时不强行等操作完成；保存未决、关闭 socket 和 timer。重开后只查询/对账。删除有未决请求的 conversation 应先提示并保护记录，不能让请求结果失去归属。

## 4. 风险

| 风险 | 应对与验收 |
|---|---|
| 派发命令被当普通 prompt | 内部命令唯一命名、pending 白名单、input 保留前缀拦截、无副作用 probe；失败禁用能力；验收零模型请求、零用户消息污染 |
| 旧 API / 自定义 pi 发行版 | 握手能力与实测兼容矩阵；本机 1.5.0 不能替代用户版本验证 |
| 超时重复执行 | 业务不暴露自动 execute retry；查询路径在类型和路由上独立，测试检查执行计数 |
| 执行成功但回执丢失 | durable 终态 + 同 ID 查询；执行/日志原子性缺口明确 UNKNOWN |
| 延迟回执误删新消息 | sessionEpoch、requestId、payloadHash、local/remote revision 与幂等提交标记 |
| 草稿在等待期间变化 | draftRevision CAS，不覆盖新输入，保留待恢复文本 |
| parent 导航语义不一致 | 执行前检查目标类型；真实 pi 集成测试覆盖 root、连续 user、未回复、已处于目标 leaf |
| TUI 在异步执行中自行变化 | 前后核验，冲突后只读对账；不作虚假的 exactly-once / 全局锁承诺 |
| 长连接资源泄漏/帧炸弹 | 有界解码、连接/队列限制、定时器销毁、旧 generation 隔离、背压 |
| 功能抽象过度 | 先实现 rewind + 一个只读操作证明复用；不做通用 RPC 框架、任意脚本执行或远程部署 |

### 4.1 必须覆盖的验收矩阵

1. idle 时 rewind 最后一条：IDEA 等待成功后只裁一次，TUI 活跃分支正确。
2. TUI 编辑器有未提交文本：不拼接指令、不自动发送、不覆盖编辑内容。
3. agent/compaction 忙、取消导航、目标不存在、重复文本歧义：明确拒绝且面板不动。
4. 同一请求重复/乱序 result、两个请求不同 seq：各自独立处理，不误丢、不二次提交。
5. execute 部分写入后断线、accepted 丢失、执行后 result 丢失：UNKNOWN + query，导航调用次数不增加。
6. 日志 RUNNING 后崩溃、导航后日志落盘前崩溃、IDEA 本地提交前后崩溃：分别恢复终态或未决，不能盲目回退。
7. 请求期间切 tab、`/new`、`/resume`、reload、Terminal 退出：旧结果不得改错会话；仍可查询原记录。
8. 等待期间编辑草稿、直接从 TUI 发新消息：保留输入，冲突可见，不盲目覆盖。
9. 旧 extension、派发 probe 失败、坏 token、超大帧、重复 peer：禁用操作并给可诊断错误，不启动模型。
10. 首条、连续 user、无回复的最后一条、目标已是 leaf：行为明确，不静默多退。
11. 查询未知 ID 是纯只读；同 ID 不同 payload 拒绝；重连不会偷偷 execute。
12. 新增只读诊断 operation 只需注册，不改 Transport；为后续 fork 验证 replacement-context 扩展接口但本轮不迁移 fork。

按仓库纪律：实现期本地以静态审查为主；用户授权 push/CI 时运行 bridge 测试并手动 dispatch dev 构建；真实 TUI 适配及断联场景需专门集成/沙箱验证。不能用 mock 通过替代真实 API 行为。

## 5. 包结构

建议 Kotlin 拆为少量职责清晰的文件，不做每种帧一个类的过度拆分：

```text
bridge/PiBridgeServer.kt             复用监听入口，分流 v1 事件与 v2 控制
bridge/BridgeProtocol.kt             DTO、错误码、能力与帧校验
bridge/BridgeConnection.kt           peer 生命周期、握手、读写与心跳
bridge/BridgeOperations.kt           请求协调、状态订阅、超时与只读恢复
bridge/OperationStore.kt             请求/结果耐久记录与保留策略
conversations/ConversationOperations.kt  rewind 业务准备与成功提交
conversations/PiConversationService.kt  对 UI 暴露语义接口，冲突入口守卫
conversations/PiConversationStore.kt    幂等提交所需兼容字段
ui/PiConversationPanel.kt            pending/unknown/conflict 展示，不处理协议
resources/bridge/pi-launcher-bridge.ts  单文件安装产物，内部按工厂封装各模块
tests/bridge-*.test.mjs              transport、coordinator、adapter、业务契约
```

TS 首期保持单文件资源和单文件安装，只在文件内部封装 Transport、RequestRuntime、OperationJournal、PiCommandAdapter、OperationRegistry、RewindOperation。不要让各操作直接读写全局 socket。若后续源码拆文件，必须先建立 bundle 产物和安装验证，仍只安装自身管理的一个 extension 文件，不向用户 extensions 目录撒依赖文件。

后续指令接入步骤：定义 versioned descriptor/schema → 注册 executor/后置核验 → 注册业务提交器 → 声明能力 → 契约测试。连接、认证、超时、未知状态、日志、恢复查询原样复用。破坏性操作没有自由选择“自动重放”的口子。
